1.1 ความเป็นมาและความสำคัญ

การไฟฟ้าฝ่ายผลิตแห่งประเทศไทย (กฟผ.) โรงไฟฟ้าแม่เมาะ เป็นหน่วยงานที่มีความสำคัญในการผลิตกระแสไฟฟ้าเพื่อตอบสนองความต้องการของประเทศ กองบำรุงรักษาโรงไฟฟ้าแม่เมาะ หน่วยที่ 10 (W10) มีหน้าที่รับผิดชอบในการดูแลรักษาเครื่องจักรและอุปกรณ์ต่างๆ ภายในโรงไฟฟ้าให้มีสภาพพร้อมใช้งานอยู่เสมอ
ในการปฏิบัติงานของ W10 มีการจัดเก็บข้อมูลงานซ่อมบำรุง การจัดซื้อจัดจ้าง การเบิกจ่ายวัสดุคงคลัง และการทำงานล่วงเวลาในรูปแบบของ Google Sheets จำนวนหลายไฟล์ ซึ่งทำให้เกิดปัญหาข้อมูลกระจัดกระจาย พนักงานต้องใช้เวลามากในการค้นหาข้อมูลจากหลายแหล่ง ขาดหน้าจอที่สามารถแสดงภาพรวม (Dashboard) และที่สำคัญคือระบบเดิมไม่มีความสามารถในการเพิ่ม ลบ แก้ไข ข้อมูล Shop Order พร้อมทั้งการแนบไฟล์เอกสารอ้างอิงได้อย่างสะดวก

1.2 วัตถุประสงค์

  1. เพื่อพัฒนาระบบแดชบอร์ดที่รวมศูนย์ข้อมูลจาก Google Sheets หลายไฟล์ให้อยู่ในหน้าจอเดียว (Unified Dashboard)
  2. เพื่อพัฒนาระบบจัดการข้อมูล Shop Order ที่รองรับการเพิ่ม ลบ แก้ไข (CRUD) และสามารถแนบไฟล์เอกสารได้
  3. เพื่อลดระยะเวลาในการค้นหาข้อมูล และเพิ่มประสิทธิภาพในการทำงานของพนักงานกองบำรุงรักษา W10
  4. เพื่อนำเสนอข้อมูลในรูปแบบภาพ (Visual Data) เช่น กราฟหรือแผนภูมิ ที่เข้าใจง่ายและช่วยในการตัดสินใจ
  5. เพื่อให้นักศึกษาได้เรียนรู้และประยุกต์ใช้เทคโนโลยีการพัฒนาเว็บแอปพลิเคชันสมัยใหม่ในสภาพแวดล้อมการทำงานจริง

1.3 ขอบเขตของโครงงาน

  1. พัฒนาระบบในรูปแบบเว็บแอปพลิเคชัน (Web Application)
  2. ใช้ฐานข้อมูลหลักจาก Google Sheets ของหน่วยงาน
  3. ระบบสามารถทำ CRUD Operations กับข้อมูล Shop Order และอัปโหลดไฟล์ขนาดไม่เกิน 10MB ต่อไฟล์
  4. ใช้ระบบ OAuth 2.0 ผ่าน Google Drive API ในการจัดการสิทธิ์การเข้าถึงและการอัปโหลดไฟล์
  5. นำระบบขึ้นใช้งานจริง (Deploy) บนแพลตฟอร์ม Vercel
  6. ระบบเปิดให้ใช้งานภายในโดยไม่ต้องมีการล็อกอิน (No Login) เพื่อความรวดเร็วในการเข้าถึง
  7. ระบบประกอบด้วย 7 หน้าหลัก ได้แก่ Home, Purchasing (Active/All), BEML Inventory, OT Summary (Overview/Employee), และ Shop Order

1.4 ประโยชน์ที่คาดว่าจะได้รับ

  1. มีระบบแดชบอร์ดที่ช่วยให้ผู้บริหารและพนักงานสามารถติดตามสถานะงานต่างๆ ได้อย่างรวดเร็วและแม่นยำ
  2. ลดข้อผิดพลาดและความซ้ำซ้อนในการจัดการข้อมูลงานซ่อมบำรุง
  3. เพิ่มประสิทธิภาพในการจัดเก็บและค้นหาเอกสารอ้างอิงที่เกี่ยวข้องกับ Shop Order
  4. พนักงานสามารถเข้าถึงข้อมูลจากอุปกรณ์ใดก็ได้ผ่านเว็บบราวเซอร์
  5. นักศึกษาได้รับประสบการณ์จริงในการพัฒนาระบบสารสนเทศสำหรับองค์กรขนาดใหญ่

2.1 Next.js and React

โครงงานนี้ใช้เฟรมเวิร์ก Next.js เวอร์ชัน 16 ซึ่งรองรับคุณสมบัติใหม่ของ React 19 โดย Next.js มีจุดเด่นในเรื่องของการทำ Server-Side Rendering (SSR) และ API Routes ซึ่งช่วยให้สามารถสร้างระบบ Backend และ Frontend ไว้ในโปรเจกต์เดียวกันได้ ช่วยเพิ่มประสิทธิภาพในการโหลดหน้าเว็บและความปลอดภัยของโค้ดที่ทำงานบนเซิร์ฟเวอร์

2.2 TypeScript

ใช้ภาษา TypeScript ในโหมด Strict เพื่อเพิ่มความปลอดภัยของประเภทข้อมูล (Type Safety) ในขั้นตอนการเขียนโค้ด ช่วยลดข้อผิดพลาดที่อาจเกิดขึ้นระหว่างการทำงาน (Runtime Errors) และทำให้โค้ดอ่านง่ายและง่ายต่อการบำรุงรักษา

2.3 Google Sheets API

เนื่องจากหน่วยงานใช้ Google Sheets ในการเก็บข้อมูลอยู่แล้ว จึงนำ Google Sheets API มาใช้เป็นฐานข้อมูล (Database) ของระบบ โดยใช้ Service Account ในการเข้าถึงข้อมูล เพื่อให้ระบบสามารถอ่านและเขียนข้อมูลได้อย่างอัตโนมัติโดยไม่ต้องให้ผู้ใช้ต้องล็อกอินบัญชี Google

2.4 Google Drive API and OAuth 2.0

ใช้สำหรับการอัปโหลดไฟล์แนบของ Shop Order ไปยัง Google Drive โดยกำหนดขอบเขต (Scope) เป็น drive.file ซึ่งให้สิทธิ์ระบบเข้าถึงเฉพาะไฟล์ที่ระบบสร้างขึ้นเท่านั้น เพื่อความปลอดภัย และรองรับการอัปโหลดไฟล์ขนาดใหญ่แบบ Resumable Upload

2.5 Vercel Platform

Vercel เป็นแพลตฟอร์มสำหรับให้บริการคลาวด์และโฮสติ้งที่ออกแบบมาเพื่อทำงานร่วมกับ Next.js ได้อย่างราบรื่น โครงงานนี้ใช้ Vercel ในการ Deploy ระบบขึ้นสู่สภาพแวดล้อมการผลิต (Production) โดยใช้ประโยชน์จากสถาปัตยกรรม Serverless และ Edge Network

2.6 Tailwind CSS v4

สถานประกอบการ

3.1 การไฟฟ้าฝ่ายผลิตแห่งประเทศไทย (กฟผ.)

การไฟฟ้าฝ่ายผลิตแห่งประเทศไทย (กฟผ.) เป็นรัฐวิสาหกิจในสังกัดกระทรวงพลังงาน มีภารกิจหลักในการผลิต จัดหา ให้บริการ และจำหน่ายพลังงานไฟฟ้าให้กับประชาชนชาวไทย โดยมีโรงไฟฟ้าและเครือข่ายระบบส่งไฟฟ้าครอบคลุมทั่วประเทศ

3.2 โรงไฟฟ้าแม่เมาะ

โรงไฟฟ้าแม่เมาะ ตั้งอยู่ที่อำเภอแม่เมาะ จังหวัดลำปาง เป็นโรงไฟฟ้าพลังความร้อนที่ใช้ถ่านหินลิกไนต์จากเหมืองแม่เมาะเป็นเชื้อเพลิงหลัก ถือเป็นโรงไฟฟ้าที่ใช้ถ่านหินลิกไนต์แห่งเดียวในประเทศไทย และเป็นแหล่งผลิตกระแสไฟฟ้าที่สำคัญของภาคเหนือ
[ภาพถ่ายประกอบ: โรงไฟฟ้าแม่เมาะ]

3.3 กองบำรุงรักษาโรงไฟฟ้าแม่เมาะ หน่วยที่ 10 (W10)

กองบำรุงรักษา W10 มีหน้าที่หลักในการรับผิดชอบงานซ่อมบำรุงเครื่องจักรและอุปกรณ์ของโรงไฟฟ้าแม่เมาะ เพื่อให้สามารถเดินเครื่องผลิตไฟฟ้าได้อย่างต่อเนื่องและปลอดภัย โดยแบ่งโครงสร้างการทำงานออกเป็นกลุ่มงานย่อย 4 กลุ่ม ได้แก่:
  • W11 (แผนกบำรุงรักษาเครื่องกล): ดูแลและซ่อมบำรุงอุปกรณ์เครื่องกลต่างๆ เช่น กังหันไอน้ำ เครื่องสูบน้ำ วาล์ว เป็นต้น
  • W12 (แผนกบำรุงรักษาไฟฟ้า): ดูแลระบบไฟฟ้า เครื่องกำเนิดไฟฟ้า มอเตอร์ และหม้อแปลงไฟฟ้า
  • W13 (แผนกบำรุงรักษาอุปกรณ์ควบคุมและทำงาน): ดูแลรักษาระบบเครื่องมือวัด ระบบควบคุมอัตโนมัติ และระบบป้องกัน
  • W14 (แผนกวางแผนและบริหารงานบำรุงรักษา): วางแผนงานซ่อมบำรุง จัดเตรียมอะไหล่ ประเมินผล และจัดการข้อมูลด้านการบำรุงรักษา
หมายเหตุ: โครงงาน W10 Dashboard นี้ ถูกพัฒนาขึ้นเพื่อสนับสนุนการทำงานของแผนก W14 เป็นหลัก ในการบริหารจัดการข้อมูลและติดตามสถานะงานซ่อมบำรุงของทั้งกอง
บทที่ 4

การวิเคราะห์และออกแบบระบบ

4.1 ความต้องการของระบบ (Requirements)

Functional Requirements

  • ระบบสามารถแสดงผลข้อมูลภาพรวมจาก Google Sheets ได้ในรูปแบบ Dashboard
  • ระบบสามารถเรียกดูข้อมูลการจัดซื้อจัดจ้าง (Purchasing) ทั้งหมดและสถานะที่กำลังดำเนินการได้
  • ระบบสามารถดูสถานะของอะไหล่คงคลัง (BEML Inventory)
  • ระบบสามารถสรุปข้อมูลการทำงานล่วงเวลา (OT Summary) รายบุคคลและภาพรวมได้
  • ระบบมีหน้าจอสำหรับจัดการงานซ่อมบำรุง (Shop Order)
  • ระบบสามารถดึงข้อมูล เพิ่ม แก้ไข และลบรายการ Shop Orderใน Google Sheets ได้
  • ผู้ใช้สามารถอัปโหลดไฟล์เอกสาร (เช่น PDF, รูปภาพ) แนบไปกับ Shop Order ได้
  • ระบบสามารถแสดงลิงก์หรือรูปภาพเพื่อเปิดดูไฟล์ที่แนบมาได้

Non-functional Requirements

  • ระบบพัฒนาด้วย Next.js และนำขึ้นระบบ (Deploy) บน Vercel
  • ระบบตอบสนองต่อผู้ใช้งานได้อย่างรวดเร็วและรองรับหน้าจอหลายขนาด (Responsive)
  • ระบบมีความปลอดภัยในการเข้าถึงข้อมูลผ่าน API และป้องกันการโจมตีเบื้องต้น
  • ขนาดไฟล์อัปโหลดสูงสุดไม่เกิน 10MB ต่อไฟล์
  • ไม่ต้องมีระบบล็อกอินผู้ใช้เพื่อความสะดวกในการเข้าถึงสำหรับพนักงานภายใน

Tier 1: Client (Browser) Tier 2: Server (Next.js) Tier 3: Database & Storage

4.3 แผนภาพกระแสข้อมูล (Data Flow Diagram)

กระแสข้อมูลหลักของระบบในการแสดงผลแดชบอร์ดและการจัดการข้อมูล มีขั้นตอนดังนี้:
กระบวนการเรียกดูและจัดการข้อมูล
ขั้นตอนที่ 1: ผู้ใช้งานเปิดหน้าเว็บเบราว์เซอร์และร้องขอหน้าแดชบอร์ด

4.7 กระบวนการอัปโหลดไฟล์ (Upload Flow)

1. ผู้ใช้เลือกไฟล์ผ่านอินเทอร์เฟซในหน้าเว็บ (ขนาดจำกัดไม่เกิน 10MB)
2. เบราว์เซอร์แปลงไฟล์เป็นรูปแบบ FormData และส่งไปยัง /api/upload
3. เซิร์ฟเวอร์ Next.js รับไฟล์ ตรวจสอบประเภทและขนาด และสร้างคำขอไปยัง Google Drive API
4. Google Drive บันทึกไฟล์ และส่งข้อมูล File ID และ WebViewLink กลับมา
5. เซิร์ฟเวอร์นำลิงก์ไฟล์ที่ได้ ไปบันทึกลงในคอลัมน์ J ของ Shop Order ใน Google Sheets

4.8 วงจรชีวิตของไฟล์แนบ (Attachment Lifecycle)

สถานะ เหตุการณ์ ผลลัพธ์ในระบบ
Pending ไฟล์กำลังอัปโหลดและรอการตอบกลับจาก Drive แสดง Loading Indicator และปุ่มอัปโหลดถูกล็อก
Active บันทึกลง Drive และอัปเดต Sheets สำเร็จ แสดงรายชื่อไฟล์และลิงก์สำหรับคลิกเพื่อเปิดดู
Scheduled Delete ผู้ใช้คลิกลบไฟล์แนบ ซ่อนออกจาก UI, ลบออกจาก Sheets และส่งคำสั่งลบไปยัง Drive

  • OT Overview: แสดงกราฟแท่งเปรียบเทียบค่าใช้จ่าย OT ในแต่ละเดือน และแผนภูมิวงกลมแยกตามแผนก
  • Employee OT: ผู้ใช้สามารถเลือกชื่อพนักงานเพื่อดูรายละเอียดประวัติการทำ OT พร้อมคำนวณค่าตอบแทนรวมและจำนวนชั่วโมงสะสม
  • Export Data: รองรับการนำข้อมูลในตารางส่งออกเป็นไฟล์ CSV สำหรับการทำรายงานส่งต้นสังกัด
[ภาพถ่ายหน้าจอ: หน้าจอระบบ OT Summary]

องค์ประกอบ UI การทำงานทางเทคนิค

File Uploader รองรับ Drag & Drop และแสดงแถบความคืบหน้า (Progress Bar) ระหว่างส่งไฟล์
Action Menu ปุ่มเปลี่ยนสถานะงาน ลบรายการ หรือเรียกดูไฟล์ที่แนบมา (เปิดแท็บใหม่)
[ภาพถ่ายหน้าจอ: หน้าจอระบบจัดการ Shop Order และฟอร์มอัปโหลดไฟล์]
นวัตกรรมของระบบ: ฟีเจอร์อัปโหลดไฟล์ของระบบนี้ ทำให้พนักงานไม่ต้องแนบเอกสารใบงานแบบกระดาษ แต่สามารถถ่ายภาพแล้วอัปโหลดเข้าระบบ และระบบจะจัดเก็บไฟล์อย่างเป็นระเบียบใน Google Drive โดยอัตโนมัติ

5.7 ความปลอดภัยและการจัดการข้อผิดพลาด (Security & Resilience)

แม้ระบบจะเป็นระบบใช้ภายใน แต่ได้มีการวางมาตรการรักษาความปลอดภัยและการจัดการข้อผิดพลาดดังนี้:
มาตรการ การนำไปใช้งานในระบบ
CORS Protection จำกัดการเรียก API เฉพาะจากโดเมนที่ได้รับอนุญาต (Vercel Domain) เท่านั้น
Environment Variables เก็บค่าความลับ เช่น Service Account JSON ไว้ใน Environment ตัวแปร ฝั่งเซิร์ฟเวอร์
Error Boundary ใช้ React Error Boundary เพื่อป้องกันหน้าเว็บล่ม (Crash) และแสดงหน้าแจ้งเตือนเมื่อเกิดข้อผิดพลาด
Rate Limiting จำกัดจำนวนครั้งในการส่งคำขอต่อนาที เพื่อป้องกันการโจมตีหรือการใช้ทรัพยากรเกินขีดจำกัด

รูปแบบข้อผิดพลาดที่ระบบจัดการได้ (Failure Modes Handling):
  • Google Sheets Quota Exceeded: ระบบจะแสดงข้อความเตือนให้ผู้ใช้รอและมีกลไก Retry แบบ Exponential Backoff
  • Network Disconnection: UI จะแสดงการแจ้งเตือนเมื่อการเชื่อมต่ออินเทอร์เน็ตหลุด และลองโหลดข้อมูลใหม่เมื่อออนไลน์
  • File Too Large: ตรวจจับขนาดไฟล์ตั้งแต่ระดับเบราว์เซอร์ หากเกิน 10MB จะปฏิเสธการอัปโหลดทันที

การทดสอบระบบ

6.1 ขอบเขตการทดสอบ (Unit Test Coverage)

เพื่อให้ระบบมีความน่าเชื่อถือและลดข้อบกพร่อง โครงงานนี้ได้มีการเขียน Unit Test ด้วยเครื่องมือ Vitest โดยครอบคลุมส่วนสำคัญของระบบ จำนวน 25 ไฟล์ทดสอบ และมี Test Case รวมทั้งสิ้น 270 รายการ โดยแบ่งกลุ่มการทดสอบได้ดังนี้:
กลุ่มการทดสอบ (Test Group) รายละเอียดการทดสอบ
UI Componentsทดสอบการเรนเดอร์ของปุ่ม, ฟอร์ม, ไดอะล็อก และตารางข้อมูล
Form Validationทดสอบกฎการกรอกข้อมูล (Zod schemas) สำหรับ Shop Order
Data Transformationทดสอบฟังก์ชันที่แปลงข้อมูลดิบจาก Sheets ให้อยู่ในรูปที่ UI นำไปใช้
API Response Formatทดสอบรูปแบบ JSON ที่ส่งออกจาก API ว่าถูกต้องตรงตาม Interface
State Managementทดสอบลอจิกการจัดการสถานะภายในของ React Hooks ต่างๆ
Error Handlingจำลองการเกิดข้อผิดพลาดจากเครือข่ายและตรวจสอบการทำงานของ Error UI
Date Utilitiesทดสอบการแปลงและคำนวณวันที่ให้ถูกต้องตามโซนเวลาของประเทศไทย

6.2 ผลการทดสอบ (Test Results)

ผลการทดสอบก่อนการติดตั้งระบบสู่สภาพแวดล้อมจริง (Production Deployment) สรุปได้ดังตารางด้านล่าง:
ประเภทการตรวจสอบ สถานะ (Status) รายละเอียดผลลัพธ์
Unit Tests (Vitest)PASS270/270 Test Cases ผ่านการทดสอบ (100%)
Type Checking (tsc)PASSไม่พบข้อผิดพลาดด้าน Type (Strict Mode)
Build ProcessPASSระบบสามารถ Build ด้วย Next.js สำเร็จ
Vercel DeploymentPASSติดตั้งระบบบนเซิร์ฟเวอร์ของ Vercel สำเร็จ
API IntegrationPASSสามารถอ่าน/เขียน ข้อมูลในระบบจริงได้ปกติ
Linting (ESLint)WARNINGพบข้อผิดพลาด 144 รายการ (Technical Debt)
หมายเหตุเชิงเทคนิค (Technical Debt): จากผลการทดสอบ แม้ว่าระบบจะทำงานได้สมบูรณ์และผ่าน Unit Test ทั้งหมด แต่ในส่วนของการตรวจสอบรูปแบบโค้ด (Linting) ยังคงมีข้อผิดพลาดอยู่ 144 รายการ ซึ่งส่วนใหญ่เป็นเรื่องของ @typescript-eslint/no-explicit-any และกฎอื่นๆ ข้อผิดพลาดเหล่านี้ถือเป็นหนี้สินทางเทคนิค (Technical Debt) ที่ไม่ได้ส่งผลกระทบต่อการทำงานของระบบ แต่อาจต้องได้รับการปรับปรุงในการบำรุงรักษาในอนาคตเพื่อให้โค้ดมีคุณภาพตามมาตรฐาน
บทที่ 7

สรุปผลและข้อเสนอแนะ

7.1 สรุปผลการดำเนินงาน

โครงงาน W10 Dashboard ประสบความสำเร็จตามวัตถุประสงค์ที่ตั้งไว้ ระบบสามารถให้บริการรวมศูนย์ข้อมูลและมีหน้าหลักทั้งหมด 5 กลุ่มหน้าเว็บ ได้แก่ หน้าแรก, จัดซื้อ, คลัง BEML, สรุป OT, และ Shop Order ระบบผ่านการทดสอบ Unit Test ถึง 270 รายการ และถูกนำขึ้นใช้งานจริงบน Vercel ที่โดเมน https://w10-jet.vercel.app/ ซึ่งช่วยให้พนักงาน W10 สามารถเข้าถึงข้อมูลซ่อมบำรุงได้อย่างสะดวกรวดเร็ว ลดเวลาการค้นหาเอกสาร และเพิ่มประสิทธิภาพในการทำงานภาพรวม

7.2 ปัญหาและอุปสรรค

ระดับผลกระทบ ปัญหาที่พบ (Findings) การแก้ไขและการรับมือ
High API ข้อมูล Mutation เปิดเป็นสาธารณะ (Public Endpoint) ยังไม่มีระบบ Authentication ที่เข้มงวด ควรเพิ่มระบบ Login ในอนาคต
High ฟังก์ชัน debugInfo คืนค่าตัวแปรสิ่งแวดล้อม (Env) ไปยังผู้ใช้ ทำการลบหรือซ่อนฟังก์ชันนี้เพื่อป้องกันข้อมูลลับรั่วไหล (Secret Leak)
Medium ปัญหา Lint Error สะสม (144 errors) รับทราบเป็น Technical Debt และกำหนดแผนปรับปรุงแก้ไข
Medium บางหน้าเว็บยังไม่ได้ถูกแปลงให้อยู่ในโครงสร้าง UI Shell ใหม่ จัดทำแผนการ Migration ให้หน้าเว็บทุกหน้ามี Layout ที่เป็นมาตรฐานเดียวกัน
Low ID ของ Google Sheets ถูกเขียนแบบตายตัว (Hard-coded) ในโค้ดบางส่วน แนะนำให้ย้าย ID เหล่านี้ไปไว้ใน Environment Variables ทั้งหมด

7.3 ข้อเสนอแนะเพื่อการพัฒนาต่อยอด

  1. ระบบยืนยันตัวตน (Authentication): ควรเพิ่มระบบ Login เช่น Google Workspace SSO เพื่อความปลอดภัยในการเข้าถึงข้อมูล โดยเฉพาะการเข้าถึงฟังก์ชันลบหรือแก้ไขข้อมูล
  2. ระบบแจ้งเตือน (Notifications): เพิ่มระบบส่งข้อความแจ้งเตือนผ่าน LINE Notify หรือ Email เมื่อมี Shop Order ใหม่ หรือมีการเปลี่ยนแปลงสถานะที่สำคัญ
  3. การจัดการ Sheet ID แบบไดนามิก: ควรสร้างระบบตั้งค่า (Settings) บนหน้าเว็บเพื่อให้แอดมินสามารถเปลี่ยน ID ของ Google Sheets ได้โดยไม่ต้องแก้โค้ด
  4. การเคลียร์ Technical Debt: ควรจัดสรรเวลาสำหรับการแก้ไขปัญหา Lint Error เพื่อให้โค้ดตรงตามมาตรฐาน TypeScript ควบคู่กับการรีแฟคเตอร์โค้ด
  5. ระบบสำรองข้อมูล (Backup): แม้ Google Sheets จะมีการเก็บประวัติการแก้ไข แต่ควรมีระบบดึงข้อมูลไปสำรองในฐานข้อมูลอื่น หรือส่งออกเป็นไฟล์รายงานประจำเดือน
  6. การทำ Migration UI Shell: ควรดำเนินการแปลงหน้าเว็บที่เหลือให้ใช้ Component UI Shell รูปแบบใหม่ให้เสร็จสิ้น เพื่อความสม่ำเสมอของ User Experience

GOOGLE_SHEET_ID_PURCHASINGID ของไฟล์ Google Sheets สำหรับงานจัดซื้อ
GOOGLE_SHEET_ID_BEMLID ของไฟล์ Google Sheets สำหรับงานคลัง BEML
GOOGLE_SHEET_ID_OTID ของไฟล์ Google Sheets สำหรับงานทำล่วงเวลา
GOOGLE_SHEET_ID_SHOP_ORDERID ของไฟล์ Google Sheets สำหรับงานซ่อมบำรุง
GOOGLE_DRIVE_FOLDER_IDID ของโฟลเดอร์ Google Drive สำหรับเก็บไฟล์อัปโหลด
NEXT_PUBLIC_APP_URLURL หลักของแอปพลิเคชัน
API_SECRET_TOKENรหัสลับสำหรับใช้เรียกใช้ API ในบางฟังก์ชันที่ต้องจำกัดสิทธิ์
ข้อควรระวังด้านความปลอดภัย: ห้ามเปิดเผยค่าของ GOOGLE_PRIVATE_KEY และ API_SECRET_TOKEN ต่อสาธารณะโดยเด็ดขาด เนื่องจากเป็นรหัสที่ใช้เข้าถึงข้อมูลระบบทั้งหมด การตั้งค่าใน Vercel จะต้องทำในส่วนของ Environment Variables (ฝั่ง Server) และห้ามใส่คำนำหน้า NEXT_PUBLIC_ โดยเด็ดขาด
