01 — EXECUTIVE SUMMARY W10 Dashboard
Section 01

Executive Summary

โครงการ W10 Dashboard เป็นการพัฒนาระบบเว็บแอปพลิเคชันแบบศูนย์รวม เพื่อเพิ่มประสิทธิภาพในการติดตามงานซ่อมบำรุง การจัดซื้อจัดจ้าง และการจัดการอะไหล่คงคลัง (BEML) ของกองบำรุงรักษาโรงไฟฟ้าแม่เมาะ หน่วยที่ 10 (W10) โดยใช้เทคโนโลยีเว็บสมัยใหม่ที่สามารถเชื่อมต่อกับฐานข้อมูล Google Sheets และ Google Drive ของหน่วยงานได้อย่างปลอดภัยแบบเรียลไทม์ โครงการนี้ถูกออกแบบมาเพื่อลดความซ้ำซ้อนของการจัดการเอกสาร ลดข้อผิดพลาดของข้อมูล และเพิ่มความรวดเร็วในการเรียกดูสถานะการดำเนินงานต่างๆ

ความสำเร็จหลัก (Key Achievements)

  • พัฒนาระบบ Shop Order ที่รองรับการจัดการข้อมูลแบบ CRUD (Create, Read, Update, Delete) พร้อมระบบแนบไฟล์เอกสาร
  • เชื่อมต่อ Google Drive แบบ OAuth 2.0 (drive.file scope) สำหรับการอัปโหลดไฟล์ได้อย่างปลอดภัย และการตรวจสอบสิทธิ์ Service Account สำหรับอ่านข้อมูลจาก Google Sheets
  • ปรับปรุง UI/UX ด้วย Tailwind CSS 4 และแสดงผลข้อมูลเชิงสถิติด้วย Highcharts และ Recharts ทำให้ข้อมูลที่ซับซ้อนดูเข้าใจง่าย
  • ทดสอบการทำงานด้วย Vitest อย่างครอบคลุม ทำให้มั่นใจในความถูกต้องของลอจิกระบบ

07 — SECURITY & RESILIENCE W10 Dashboard
Section 07

Security & Resilience

รูปแบบการยืนยันตัวตน (Authentication Model)

  • Google Sheets: ใช้ Service Account ด้วย GOOGLE_CLIENT_EMAIL และ GOOGLE_PRIVATE_KEY สำหรับเข้าถึงข้อมูลแบบ Background โดยไม่ต้องให้ผู้ใช้ล็อกอิน
  • Google Drive: ใช้ OAuth 2.0 (Scope: drive.file) ซึ่งแอปจะเข้าถึงได้เฉพาะไฟล์ที่แอปสร้างขึ้นเองเท่านั้น ป้องกันการเข้าถึงไฟล์อื่นในไดรฟ์ของหน่วยงาน

มาตรการความปลอดภัย (Security Measures)

Security Area Implementation Details
Input Validationใช้ Zod Library ตรวจสอบ Type และ Format ข้อมูลก่อนส่งเข้า Database
Secret Handlingเก็บ Key ทั้งหมดใน Environment Variables ไม่อยู่ใน Source Code
URL Allowlistอนุญาตเฉพาะ URL ที่กำหนดใน CORS policy ป้องกัน Cross-Origin attacks
Attachment Ownershipไฟล์แนบเป็นแบบ Read-only สำหรับผู้มีลิงก์เท่านั้น
Traffic ControlNext.js API Routes รองรับ Rate Limiting จาก Vercel (WAF)
Cleanup AuthCron job ลบไฟล์ขยะ ทำงานผ่าน API ที่ต้องมี Secret Token ยืนยัน

สถานการณ์รับมือความล้มเหลว (Failure Modes)

  1. Google API Quota Exceeded: ระบบจะใช้ข้อมูล Cache เดิม (SWR) และแสดงข้อความเตือนให้ลองใหม่
  2. Upload Partial Success: หากอัปโหลดไฟล์ผ่าน แต่บันทึก Sheets ไม่ผ่าน ไฟล์นั้นจะมีสถานะ Pending และถูกลบโดย Cron job
  3. Network Timeout: UI จะแสดง Skeleton loaders และมีปุ่ม Retry
  4. Invalid Authentication: API จะตอบกลับ 401 และหน้าเว็บแสดง Fallback UI
  5. Corrupted Sheet Data: ระบบ Validation จะกรองแถวที่ข้อมูลผิดพลาดออก (Skip) แทนที่จะทำให้เว็บล่มทั้งหน้า

09 — FINDINGS & RECOMMENDATIONS W10 Dashboard
Section 09

Findings & Recommendations

ข้อค้นพบและปัญหาที่พบ (Findings)

Severity Issue Description Impact
High Google Sheets API Rate Limit (60 requests / minute) หากมีผู้ใช้งานพร้อมกันจำนวนมาก อาจเกิดคอขวด ทำให้ข้อมูลโหลดช้า หรือ Error ได้
Medium AppShell ยังไม่ครอบคลุมทุกหน้า ความไม่สม่ำเสมอของ UX ระหว่างหน้า /ot-employee กับหน้าอื่นๆ
Medium ไฟล์รูปภาพที่ลากวางบางครั้งมีขนาดใหญ่เกินไป สิ้นเปลืองพื้นที่ Drive และใช้เวลาอัปโหลดนาน
Low ESLint Warnings (Tech Debt) ความสะอาดของโค้ด ไม่ส่งผลต่อการทำงาน แต่ควรแก้ไขในระยะยาว

ข้อเสนอแนะสำหรับการพัฒนาต่อ (Recommendations)

  • Caching Strategy: ควรเปิดใช้งาน Next.js ISR (Incremental Static Regeneration) ร่วมกับ Redis Cache เพื่อลดภาระการเรียก Google Sheets API ทุกครั้งที่มีการ Refresh
  • UI Refactoring: ดำเนินการย้ายหน้าเว็บที่เหลือเข้าสู่โครงสร้าง AppShell ให้ครบถ้วน เพื่อให้ Sidebar และ Header ทำงานประสานกันอย่างสมบูรณ์
  • Image Compression: เพิ่มไลบรารีบีบอัดรูปภาพฝั่ง Client (เช่น browser-image-compression) ก่อนส่งไฟล์ไปยัง /api/upload
  • Database Migration: หากข้อมูล Shop Order มีจำนวนเกิน 10,000 แถว ควรพิจารณาย้ายจาก Google Sheets ไปใช้ฐานข้อมูลจริง เช่น PostgreSQL (Supabase) หรือ MongoDB
  • Code Cleanup: จัดการเคลียร์ ESLint warnings ทั้งหมดก่อนการปิดโปรเจกต์ (Handover)
  • Role-Based Access Control (RBAC): เพิ่มระบบ Login และสิทธิ์การใช้งาน (Admin, Manager, User) เพื่อจำกัดการเข้าถึงเมนูบางส่วน

  1. ตรวจสอบว่าหน้า Home สามารถโหลดกราฟได้ครบถ้วน
  2. ทดลองสร้าง Shop Order ใหม่ 1 รายการ และอัปโหลดไฟล์ขนาดเล็ก
